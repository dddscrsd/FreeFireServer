# BUILD SPEC — Go CS match server: single-player+bot → 2-8 player multiplayer

## 1. PROBLEM STATEMENT

**What works today (verified in Report C):** A single UDP client joins via cmd 439/440 (`handleJoinMatchPost`), `resolvePlayer` hands it the baked identity entity `0x01000001` / RepID `1000` / faction `0` / team-hibyte `1`, the server immediately spawns one passive bot (`botEntityID 0x02000002`, `botRepID 1001`, `botFaction 1`) via a second cmd 101, and `startCSSync` launches a per-session `csSyncLoop`. That loop drives the full CS round machine (Warmup→Prepare→Fight→Post→next round→MatchEnd), streams cmd 900 (`priPayload`) + cmd 901 (GRI) every ~300 ms to the one client, seeds a 2-key HP map `{playerEntityID, botEntity}` (`initHP`), and decides the round on `localWon := entityHP(playerEntityID) > 0` (i.e. "bot died"). Damage, zone (`runSafeZone`), medkit, gloo, loot, shop all function against that one session.

**The precise gaps for N players:**
1. **No match object.** State that must be *shared* (round, phase, arena, `teamScore[2]`, HP map, zone, walls, ground loot) lives on the per-connection `session` (Report C §1). Two clients = two disjoint private matches; nothing is broadcast.
2. **Identity collision.** `resolvePlayer` (player.go 73-101) hardcodes `EntityID: playerEntityID` and never reads it from the JWT. Every client becomes `0x01000001`/RepID `1000`/team `1`. Report B's spawner dedups on PlayerID (`HOOCHDLKOOG.ContainsKey` @spawner `0x1a39ae4`) — two identical PlayerIDs → the 2nd is dropped with a warning; identical userids → the client's `IsLocalPlayer` (@0x189d980) treats the remote as *itself*.
3. **Single-destination I/O.** `s.write`→`conn.WriteToUDP(wire, s.remote)`. No fan-out primitive.
4. **The bot is the win condition.** `killEntity` credits `roundKills` only for `killer==playerEntityID && victim==s.botEntity`; `streamPhase` exits Fight on `entityHP(s.botEntity)==0`; `matchEnd`/`roundResult` derive VICTORY/DEFEAT from the one local player. Real opponents don't exist in the model.
5. **Damage lands in the wrong place.** `handleTakeDamage`/`applyDamage` mutate *the shooter's own* `s.hp` map. A hit on a remote player must mutate the victim's HP in shared state and fan the result to all.
6. **No allocators.** Only `nextUIDLocked` (item uids) and `nextWallLocked` exist. No entity-id/RepID/team generator (the `PlayerIDGenerator` hibyte=team/low24=slot scheme is described in comments only).
7. **No lobby/roster.** Join instantly builds a private 1v1-vs-bot with a per-*join* random arena (`choosePlayerSpawn`), never a per-*match* arena, and never broadcasts the newcomer's cmd 101 to others.

## 2. TARGET ARCHITECTURE

Adopt the **actor-per-match** model from Report D. One goroutine owns all mutable match state; net-recv only parses and posts events; each connection gets one writer goroutine that owns its seq/order. This deletes the 3 sleeping per-player goroutines (`csSyncLoop`/`serverTimeLoop`/`runSafeZone`) and all three per-session mutexes (`mu`/`invMu`/`hpMu`).

### New types

- **`Match`** (match.go) — `id`, `mailbox chan event` (buffered ~256), `quit`, `done`, `players map[uint32]*Player` (keyed entityID), `ids idAllocator`, `mgr *Manager`, plus the promoted shared state: `state` (Lobby|Warmup|Running|Ended), `phase uint16`, `phaseDeadline time.Time`, `round int`, `teamScore [2]uint8`, `matchStart time.Time`, `arena csArena`, `zone zoneState`, `walls []*iceWall`, `wallSeq`. **No mutex** — every field mutated only inside `run()`.
- **`Player`** (player.go) — per-connection game state: `addr`, `info message.PlayerInfo` (cosmetics from prepare_token), `isBot bool` (out==nil filler), allocated `entityID/repID/team/faction`, combat/economy (`hp/maxHP/alive/pos/face/coins/award/roundKills/equipment/weapons/clientUIDs/itemOnHand/uidCounter/containers`), and `out *Writer`.
- **`Writer`** (writer.go) — per-connection transport: `conn/addr/key/ch chan outItem/seq/order`. Its goroutine is the sole owner of seq/order, so `session.mu` disappears. `outItem` is either a pre-framed VAR broadcast (`raw`) or a logical reliable `{cmd, body}` it frames with this conn's next seq/order.
- **`Manager`** (manager.go) — `matches map[uint64]*Match`, `joinable []*Match`, `byAddr map[string]*Player` (recv demux), `nextID`, `conn`, `factory MatchFactory`; guarded by one small `sync.Mutex`.

### The single tick-based broadcast loop

`Match.run()` is one `select` with three tickers (rates chosen by change frequency):

| Stream | Our cmd | Rate | Encode |
|---|---|---|---|
| Movement relay (remote positions) | **900** (replication channel — see §3, per Report B, *not* 145) | ~16 Hz / 60 ms | once/tick, fan out |
| PRI + GRI (HP/coins/score/phase) | **900 + 901** | ~5 Hz / 200 ms | once/tick, fan out |
| Server clock | **1000** | ~4 Hz / 250 ms | once/tick, fan out |

Discrete **reliable** events (join **101**, bindPRI **118**, death **107**, zone-change **117**, round-result **409**, inventory **174**, teleport **145**) are *not* on a ticker — they fire from `advancePhase`/handlers per-player via `p.out.SendReliable`.

**Encode-once is safe** (Report D verified in packet.go): VAR packets (900/901/1000) are `SendOption=4, Flags=0`, CRC7 over body only, no addr, no per-conn seq → identical bytes for every player. `broadcast(wire []byte)` enqueues the *same slice* to each `Player.out` non-blocking (drop-on-full; superseded next tick). `message.SyncPRI([]PRIEntity)` already packs many entities into one cmd 900.

Two structural conversions replace the sleep-driven code:
- `runSafeZone` goroutine → `stepZone(now)` called inside the state tick (recompute shrink radius; on the 2 s damage cadence walk the player list applying out-of-zone damage). Must preserve the `zoneClientLag` compensation.
- Blocking `csSyncLoop`/`streamPhase`/`roundTransition` (`time.Sleep`) → deadline-driven `advancePhase(now)`: `now >= phaseDeadline` (or "enemy team eliminated") triggers the edge transition and its reliable sends.

### Concurrency model — **single-owner mailbox, not RWMutex**

Every state change (join/leave/damage/pos/purchase/wall/pickup/phase-edge/tick) serializes through `run()`'s `select`. Producers post typed events; droppable (position) uses non-blocking send, must-not-drop (join/leave/damage/purchase) blocks. Rationale: it deletes the three ordered mutexes by construction; the tick is a hot full-map iterating reader while match state is write-heavy (every hit/pos/buy), so an RWMutex degenerates to a plain serializing mutex anyway; and the parallelism you want is *across matches* (independent goroutines spread over cores), not within one match (shared round/zone/score). The one rule: handlers never block inside `run()` — all output is a non-blocking enqueue to a `Writer`. The **Manager** keeps a plain `sync.Mutex` (tiny create/route/reap sections only) — that's correct and off the hot path.

### Bot removal/replacement

During bring-up the bot survives as a seeded `Player{isBot:true, out:nil}` on team B so `broadcast` skips it (`out==nil`) and today's CS fight keeps passing. The `idAllocator` seeds it to reach `minToStart=2`. As real opponents join, the bot slot is not allocated; `advancePhase`'s Fight-exit changes from "botEntity dead" to "one team fully eliminated" (§3 death flow), and every hardcoded `s.botEntity`/`botRepID`/`respawnBot`/`killEntity` special-case is replaced by iteration over `players`.

## 3. SYNC FLOWS (our cmd numbers)

### (a) Two-way join broadcast — cmd 101 (`GKBDLJFGGMI`, handler `OFEBIEPAIKH` @0x1933de8)
On `evJoin{newcomer}` handled inside `run()` (authoritative admission, re-checks `len(players)<8 && state<=Warmup`):
1. Allocate the newcomer's `entityID/repID/team/faction` (§4).
2. **Download:** send the newcomer one cmd 101 per *existing* player (unique `MIJOCMKONAD` userid + unique `IHAAMHPPLMG` PlayerID with correct team hibyte), so it spawns all of them. Spawner `LONDNBHBPDO` @0x1a39ae4 self-registers each RepID (Report B §2 — **no cmd 118 needed for the spawn itself**, the pawn binds its own UniqueID via `RegisterRepEntity` @0x1c9fc40).
3. **Broadcast:** send the *newcomer's* cmd 101 to every existing player's `out` → they spawn the newcomer.
4. **BindPRI cmd 118, per-recipient:** each client's cmd 118 must list **its own entity first** (client adopts the first `EntityType=1` binding as self — Report C `bindPRIs` note), then the roster. This replaces `bindPRIs` binding exactly `{playerRepID, botRepID}`.
5. Reply ok; the next state tick's `encPRI` includes the newcomer automatically.

**Critical (Report B §5):** for a remote, *both* userid (`MIJOCMKONAD`) and PlayerID (`IHAAMHPPLMG`) must differ from the recipient's own, or `IsLocalPlayer` @0x189d980 mis-routes it as self. Fixes the `resolvePlayer` bake in player.go 73-101.

### (b) Per-player PRI — multi-entity cmd 900 (`DNCBMEDLPGP` @0x194e080, `GetRepEntity` @0x1c9fe48)
`encPRI()` builds ONE cmd 900 for the whole match each 200 ms state tick: loop `players`, skip dead bot, append `message.PRIEntity{RepID: p.repID, Block: PRIHPBlock(p.hp, p.maxHP, uint16(p.coins), uint16(p.award), PackScore(teamScore[p.team], teamScore[p.team^1]), p.faction)}`. Wire format is `[u32 RepID][FixUInt16 len][payload]…` to EOF; unknown RepIDs are skipped by the client. Fixes `priPayload` (cssync.go 201-223) which emits exactly local+bot. **Each player's own coins ride in their own RepID block** (Report D gotcha) — do NOT stamp the local player's coins onto every block; the shop UI reads only the recipient pawn's PRI. Sent to: **all connected players** every state tick. On-change immediacy for damage is added by an out-of-band 900 right after applying a hit (below).

### (c) Movement relay — **cmd 900 replication channel** (apply `LBCGDBDLEKI` @0x1fa7f54)
This corrects Report D's 145/144 assumption. Report B §3 is explicit: remote movement is applied by `PushPlayerSyncedStateData` @0x1fa8990 / `PushPlayerSyncedOptimizedStateData` @0x1fa7938 / `PushPlayerSyncedPosition` @0x1fa872c, registered as the pawn's **replicated-property change handlers** — i.e. it rides the same replication/state-sync channel as PRI (cmd 900), gated by `if(!IsLocalPlayer)` and a **monotonic per-player move sequence** (`if (KINJCKMOGIM < incomingSeq)`), then interpolated (never snapped). The 60 ms move tick therefore emits a cmd-900-class synced-state block per player carrying compressed position (`CCIKDFGDBAM`), body-move dir, aim dir, move-platform id, movement state (`GHGCGGOLKIP`), speed (`LMNBBBCKMGB`), and the incrementing sequence. Server ingests each client's own movement via **cmd 1001** upstream, stores `pos/face/moveState/seq` on that `Player`, and relays *others'* state on the tick. **Never echo a player's own cmd 1001 back** (the `if(!IsLocalPlayer)` guard would drop it anyway). Discrete forced teleports (spawn, round transition) remain **cmd 145** (`ForceTeleport`), reliable — distinct from the interpolated relay.

**Open item (see §7):** exact byte layout of the synced-movement 900 sub-block vs. the HP 900 block, and whether they share one packet or interleave, needs a live capture — our `message` layer currently only builds the HP `PRIHPBlock`.

### (d) Inter-player damage — client reports via cmd 106, server authoritative
Client→server hit report is **cmd 106** (Report B §4). Handler posts `evDamage{attackerEID, victimEID, weapon, part, dmg}` to the match mailbox. Inside `run()` (single-owner, replaces `handleTakeDamage` writing the shooter's own map): dedup the shot (client sends ~4×), recompute authoritative damage server-side (keep `combat.go` `applyDamage` math, apply armor), subtract from **the victim `Player`'s** `hp` in shared state. Then: (i) push authoritative HP immediately via an out-of-band cmd 900 for the victim's RepID to all players (don't wait for the tick); (ii) the client renders the health-bar/hit-FX purely from that replicated `UInt16` HP drop — **no per-observer damage packet** (Report B §4). `hp<=0` → death branch.

### (e) Death / respawn
**Death — cmd 107** (`Dead` @0x1fb3358, resolved by PlayerID via `KAGPBMINBIJ` @0x1a1fad4). On lethal damage, set victim `alive=false`, `hp=0`, bump killer `roundKills`, and **broadcast one cmd 107 to every player** carrying victim PlayerID + killer PlayerID (fixes `killEntity` combat.go 99 two-identity branch). Next `encPRI` omits the dead entity's live block per current dead-drop behavior. Optional knockdown (team mode): **`NKDBFGLPCCF`** (handler `JFCAKCFEAEN` @0x193ed20, `SyncKnockDown` @0x1fb3464) carries victim PlayerID + attacker PlayerID + weapon — only if we enable revive; CS default is direct death.

**Respawn is per-round, not per-death** (CS, not battle-royale). On round transition `advancePhase` reseeds every player's `hp=maxHP`, `alive=true`, repositions all players to their team's arena gate via **cmd 145** teleport, and streams fresh PRI. Replaces `roundTransition`/`respawnBot`/`respawnLocalPlayer` two-entity reseed (round.go). Round ends when one team's players are all dead (replaces `entityHP(botEntity)==0`); match ends on `teamScore` reaching `roundsToWin` → **cmd 103** match end + **cmd 409** round-coin popup (per MEMORY).

## 4. IDs / TEAMS / CAPACITY

`idAllocator` (ids.go, Report D §5) preserves `PlayerIDGenerator` semantics confirmed in player.go: **entity-id hibyte = team, low-24 = slot**; teammates share hibyte. Bands: team A → hibyte 1 (matches today's `0x01xxxxxx`), team B → hibyte 2 (matches bot `0x02xxxxxx`), low-24 = per-team slot 1..4. RepIDs disjoint band `1000 + globalSlot`. Gloo/prop RepIDs stay high (`wallSeq`-based 5000+) so they never collide with players.

```
maxPerTeam=4, maxPlayers=8, minToStart=2, playerRepBase=1000, teamShift=24
allocate(): balanced (fill smaller team; tie→team 0), lowest-clear slot, banded entityID
            = (uint32(team+1)<<24)|(slot+1); faction=team; repID=1000+lowestClearRep; ok=false at 8
free():     clear slot+rep bits AFTER the player is removed and a leave/despawn is sent
```

- **Cap 8 / min 2:** `allocate` refuses the 9th (`ok=false`); match stays in Lobby until `≥minToStart`. Seed a bot-`Player` on team B to reach 2 during bring-up (reproduces today's static-bot fight exactly).
- **Balanced 4v4 max, self-healing** on leave.
- **Reuse safety:** free slot/RepID only after removal + despawn so no in-flight PRI references a freed RepID; next `encPRI` just omits it. O(1) bitset alloc/free.
- **"Self is first" is a per-connection send concern** (cmd 118 ordering, §3a), *not* an allocator concern — the allocator only guarantees correct team hibytes + unique RepIDs.
- **Clean seam for "match full → new process":** at 8, `allocate` returns `ok=false`; the Manager creates a fresh match via `factory.New()` (§5). The 8-cap is the exact boundary the process-per-match feature keys on.

Replaces player.go consts `playerEntityID/playerRepID/localFaction` and round.go `localTeamID=1/enemyTeamID=2` with allocated per-player values; the per-*join* arena pick (`choosePlayerSpawn`) becomes a per-*match* arena chosen once at match creation and given to every joiner.

## 5. MULTI-MATCH SAFETY

`Manager` (manager.go) routes datagrams: recv goroutine parses join (439/440), `resolvePlayer` verifies the token, then `mgr.Assign(player)` under `mu` picks a `joinable` match (or `factory.New()`), posts `evJoin{player, replyCh}` to its mailbox, releases `mu`. The **match goroutine is authoritative on admission** (re-checks `<8 && state<=Warmup`, allocates, spawns both directions, replies ok/bounce). On bounce (filled between pick and admit) the Manager retries/creates — race-free without the Manager tracking exact live counts. `byAddr` demuxes gameplay packets to the owning `Player`→`Match.mailbox`.

**Reap:** when the last player leaves or match ends, the match goroutine calls `mgr.retire(id)` (short `mu`: delete from `matches`/`joinable`) and returns from `run()` (closes `done`). Add a **grace window** before reaping an emptied-but-not-ended match so the cmd-5 reconnect path (`handleHello`, which today resumes by addr) can re-attach to the *same* match. Fixes `handleHello` re-adopting the baked identity — reconnect must re-resolve the real player and rejoin their existing match.

**Capacity per box (Report D census):** before = `1 recv + ~3×P` sleeping goroutines; after = `1 recv + M match + P writers`, none on `time.Sleep` (all park on `select`). 8 matches × 8 players (P=64): ~192 → 73 goroutines. Parallelism across matches; serial within a match (a single CS match's few-hundred-events/sec never strains one goroutine). Practical ceiling is bandwidth/CPU of the encode-once fan-out, not goroutine count — comfortably dozens of concurrent matches on one machine.

**Process seam (define now, ship local):** Manager only ever talks to a `MatchHandle` interface — `Post(event)`, `Capacity()`, `Done()`. `factory.New()` returns a `*localMatch` wrapping the in-proc `*Match`+mailbox today; a later `procMatch` spawns an OS process on its own UDP port behind the same interface, routing untouched.

# FF reference server (`udp.py`) — multiplayer sync architecture

Design/data-flow only. Message types are named by role (their numeric opcodes are omitted since your client differs); every claim cites the function/line.

## 1. Match/room data structure

- **`Match` class** (line 3095). One instance per game. Core member: `self.players = {}` — a dict **keyed by `user_id` → a plain player dict** (line 3101). Alongside it: `self.state` (a `MatchState` enum WAITING/STARTING/IN_PROGRESS/FINISHED, line 2791), `match_id`, `map_id`, `game_mode`, `id_generator` (a `PlayerIDGenerator`), `next_rep_id` (starts at 1000), a `threading.Lock`, plus all world state (loot list, `oildrums`, `icewalls`, `vehicle_states`, `observers` dict = downed/dead spectator→target, `admin_observers`, safezone fields, and live `player_stats`/`kill_feed`).
- **Per-player state** is built in `add_player` (dict literal at line 3423): `user_id`, `player_id`, `nickname`, `addr`, `team_index` (= the HIBYTE of `player_id`), `position` (int x,y,z tuple), `rotation`, `velocity`, `direction`, `phys_state`/`phys_pose`, `aim`, `inventory` (list; seeded with a fist item), `attachments`, `item_on_hand`, vehicle fields, `health` (200), `rep_id`, equipment (vest/helmet/bag durabilities), `cur_ep`/`max_ep`, and knockdown/revive fields. So HP/pos/inventory/addr all live in this one dict.
- **Two IDs per player, deliberately separate.** `player_id` is a 32-bit composite (`PlayerIDGenerator.generate_player_id`, line 2807): **HIBYTE (bits 24-31) = team id**, low 24 bits = a per-player counter. In solo each player gets a unique HIBYTE, i.e. is its own one-man team; `team_index` is that HIBYTE. `rep_id` is a **separate sequential replication id (1000+)** used only on the state channel; a "BindPRI" message maps `player_id ↔ rep_id` on the client.
- **Lookups** (lines 3507-3522): `get_player(user_id)` = dict.get; `get_player_by_id(player_id)` = linear scan; `get_all_players()` = `list(self.players.values())` (snapshot, lock-free reads under the GIL).
- **`MatchManager`** (line 3851): `self.matches = {}` keyed `match_id → Match`.

## 2. Player JOIN + the two-way introduction

- **Entry**: the JOINMATCH handler (line 18514) validates the TCP hand-off / reconnect, then `match_manager.find_available_match(map_id, game_mode)` (line 19120) picks or creates the room. `session["match_id"]` and `user_sess["match_id"]` are set.
- **Add**: `match.add_player(user_id, nickname, addr)` (line 19185 → 3396). Under lock: if `user_id` already present it's a **reconnect** (refresh addr, mark `_reconnecting`). Otherwise it mints `player_id = id_generator.generate_player_id()` (unique HIBYTE), assigns `rep_id = next_rep_id++`, default spawn/health/inventory, and `team_index = HIBYTE`.
- **Teams**: roster is read from Redis (`prepare_match_from_roster`); for duo/squad the `player_id` is regenerated with `generate_player_id_same_team` so teammates **share a HIBYTE** (lines 19217-19227). Solo keeps unique HIBYTEs.
- **The newcomer's own setup**: handler sends it scene info + its own inventory + BindPRI, registers it into the per-match state loop (`start_pri_replication`, line 19382), records `addr_to_match[addr]` (line 19387), then calls `sync_players_in_match` (line 19394).
- **The two-way introduction** — `sync_players_in_match` (line 14484) just enqueues onto a single dedicated worker thread; the real work is `_do_sync_players` (line 14574):
  1. Send the newcomer **its own** PlayerJoin (line 14587).
  2. Loop over every existing player (lines 14632-14685) and for each do **both directions**:
     - **BROADCAST** — send the *newcomer's* PlayerJoin to the existing player (line 14658) → existing players learn the newcomer.
     - **DOWNLOAD** — send the *existing* player's PlayerJoin to the newcomer (line 14667) → newcomer learns every existing player.
     - Plus cross **inventory** sync in both directions (lines 14677-14683). PlayerJoin payloads are built once per uid and cached (`_get_cached_player_join_payload`, line 14556).
  3. After a 150 ms settle, **re-send BindPRI** (the `player_id↔rep_id` map) to all existing players *and* the newcomer, so everyone's rep-id table now includes the new entity (lines 14703-14728).
- **Late join** (match already IN_PROGRESS): broadcast of the newcomer is limited to **teammates** (`team_only_broadcast`, line 14581) because enemies were already introduced at battle start; downloads to the newcomer are unrestricted.

## 3. Position / movement sync

- **Receive** — the PlayerState handler (line 21632). Resolves match+player from the session, drops it if the player is dead (line 21651), unpacks pos/rot/dir/vel/phys/aim (line 21662). After anticheat (speed/teleport/ground/phys-lock), it **writes the fields atomically into the player dict** — `position`, `rotation`, `direction`, `velocity`, `aim`, `phys_state`, `phys_pose` (lines 22206-22268), stamps `last_update_mono`, and **pushes the fresh state into the match interpolation buffer** (`loop._interp_buffer.push`, line 22312).
- **Key point: the receive handler does NOT relay.** Relay is a dedicated **per-match thread `MovementSyncLoop`** (line 12199), tick ≈ 33 ms / 30 Hz (`run`, line 12265). Each tick `_sync_all_players` (line 13004):
  - reads an **interpolated** state per player from the buffer (`get_interpolated_state`), packs a fixed per-player block;
  - **builds ONE combined payload containing every player's block and sends that same unreliable packet to all players** (lines 13118-13148) — O(N), not O(N²); the client ignores its own block by id. Splits into ≤32-player chunks past the MTU (line 13149).
  - Optimizations: delta-compression skips stationary players except every 10th tick (line 13061); an optional proximity **visibility filter** sends each recipient only visible players' blocks (lines 13185-13245); disconnected-but-moving players are dead-reckoned forward (lines 13034-13047).
- Started once, when the first player joins (`start_movement_sync`, line 19424), and runs across WAITING/IN_PROGRESS; it exits when state becomes FINISHED (line 12271).

## 4. State replication (PRI equivalent — HP/score/armor/EP)

- **Dedicated per-match thread `PRIReplicationLoop`** (line 11565), interval **0.15 s (~6.6 Hz)**. It holds `self._player_addrs` (addr → msg_key/secret), populated by `start_pri_replication` (line 11873) — **one loop per match**, players registered into it. Runs in every state so weapons/HP are visible even in the lobby.
- Each tick `run()` (line 11602): **(a)** broadcast the **alive-count** (GRI) to everyone (lines 11614-11624); **(b)** build a per-entity state block for every joined player from live dict values — HP (or `knocked_hp` if downed), armor durabilities, `item_on_hand`, EP, `kill_count`, status/buff/fire-state (`build_pri_hp_block`, line 11685), keyed by `rep_id`; **(c)** send the multi-entity state packet to each player, **re-reading fresh HP at send time per recipient** (lines 11739-11779) to avoid a race where a damage handler's HP update is reverted by a stale pre-built snapshot.
- So replication is **periodic full-state broadcast** (not on-change); the snapshot it keeps is only used to decide replay recording. **On-change immediacy** is added by the damage path: it calls `pri_loop.set_health(new_hp)` and sends an immediate state packet right after applying damage (lines 21288-21363). Spectators get the observed target's block relabeled with the *observer's* rep_id (lines 11789-11830).

## 5. Inter-player damage — server authoritative

- **Receive**: TakeDamage handler (line 20337). The **attacking** client reports victim `player_id`, base damage, weapon, body part, attacker `player_id`, fire/target positions. Guards: no damage before IN_PROGRESS or while attacker is onboard-plane/zipline/not-battle-started (lines 20341-20369); **dedup** of the same shot by `(tick, attacker, victim)` (line 20465, since the client sends it ~4×); reject client zone-damage and cheat-flagged weapon ids.
- **Apply (authoritative)**: the server **recomputes real damage** = base × body-part multiplier server-side (`get_real_damage`, line 20412; it prefers its own value but caps to the client-reported number to block inflation). It looks up the victim in `match.players`, runs `apply_damage_with_armor` (line 21235) to reduce damage and decrement vest/helmet durability, then **subtracts from the victim's `health` in the dict** (or `knocked_hp` if downed) (lines 21242-21287). Records damage + aimbot stats.
- **Broadcast**: pushes authoritative HP via `pri_loop.set_health` + an immediate state packet (lines 21288-21363); forwards a TakeDamage packet to the **victim** (line 21297) and to spectators/admin observers (lines 21378-21398); broken armor is removed from inventory and broadcast as equipment-change + inventory-sync to all (lines 21316-21350). The attacker never writes victim HP directly — client only *requests*, server validates+applies+broadcasts. `health <= 0` falls into the death/knockdown branch.

## 6. Death + respawn broadcast

- This is **battle-royale: there is no respawn** — death is terminal. On lethal damage (line 21405), `match.should_knockdown` decides:
  - **Team mode with a live teammate** → `knockdown_player` (line 21420): downed, not dead; `knocked_hp` bleeds out via the consolidated bleedout tick; can be revived. Knockdown and revive are broadcast to all (`send_knockdown_to_all` line 7772, `send_revive_to_all` line 7816, `revive_player` line 7965). This revive is the only "respawn-like" mechanic.
  - **Already downed and shot again** → `finalize_knocked_player` (line 21439) → real death.
  - **Otherwise direct death** (lines 21447-21616): set `is_dead=True`; choose an **observe target** (alive teammate → else killer → else nearest alive) and migrate/register spectators (`observer_migrate`/`observer_start`, line 21467); bump killer `kill_count` and push the killer's updated state; record kill/aimbot; **drop the dead player's inventory as a loot container** (`drop_death_loot`); then **broadcast a Dead message + an observe message to EVERY player** in the match (loop, lines 21566-21575) plus admin observers; recompute and broadcast the new **alive-count** (lines 21598-21609); call `check_match_should_end`.
- **`force_kill_player`** (line 8141) is the system-death equivalent (safezone/fall/anticheat): same shape — set `is_dead`/`health=0`, zero HP in the PRI loop, drop loot, pick an observe target, broadcast Dead + Quit to all with throttle.

## 7. Match lifecycle with multiple players

- **States**: `MatchState` WAITING → STARTING → IN_PROGRESS → FINISHED (line 2791).
- **Start gating**: when the first player joins a WAITING room, `room_fill_started` is set and a `schedule_room_fill_timeout` thread starts (lines 19466-19475). Fill window ≈ `ROOM_FILL_TIMEOUT` (20 s). If the room hits `MAX_PLAYERS_PER_ROOM` first → immediately STARTING + `schedule_battle_start` (lines 19478-19482). Else at timeout, if ≥1 player present → STARTING + `schedule_battle_start` (lines 14847-14860). **Effective minimum to start is 1** (rooms are padded with AI/bots).
- **Countdown/start**: `schedule_battle_start` (line 14862) runs a per-second countdown thread (`BATTLE_START_DELAY`) sending countdown + AI-info to all, then flips to IN_PROGRESS, sets `start_time`, resets each player's `battle_start_sent`, **teleports all players to the shared plane spawn** (line 14957), and in a throttled per-player loop (line 15173) sends scene info, BindPRI, starts PRI replication, vehicle/oildrum vars, visibility, and alive-count.
- **Ticking model**: **one `MovementSyncLoop` thread per match (30 Hz)** and **one `PRIReplicationLoop` thread per match (~6.6 Hz)**, plus a SafeZone loop thread; EP-regen, underground, anti-ESP and bleedout are **folded into the movement loop as sub-routines** (lines 12310-12338) to cut GIL contention. These are sleep/interval background threads. Actual packet handling is **event-driven** per match (`MatchThread` queue, see §8), not part of these loops.
- **Teams**: solo = unique HIBYTE per player; duo/squad share HIBYTE via roster; `is_team_mode`/`alive_team_count` drive team logic and knockdown.
- **End**: after each death, `check_match_should_end` (line 7736) — solo ends at `alive_count == 1`, team ends at `alive_team_count == 1` — returns the winner PID. Then `cleanup_all_match_sessions` (line 4393) / `schedule_match_end` (line 16164) sends match-end/rank, saves stats (Redis/Mongo), and tears down; the loops see FINISHED and exit.

## 8. Match manager — routing, creation, cleanup

- **`MatchManager`** (line 3851): `matches` dict, `next_match_id` persisted in Redis. `find_available_match` (line 3894) scans for a WAITING match matching `map_id`+`game_mode` with `len(players) < MAX_PLAYERS_PER_ROOM`, else creates a new `Match` and registers it (and with the reconnect manager). `get_match` is O(1) dict access (line 3931, deliberately lock-free — one match per process). `remove_match` under lock (line 3938).
- **Routing / threading**: a UDP dispatcher receives datagrams; a **`LobbyThread`** (line 3036) handles hello/join, and each match has its own **`MatchThread`** with a `packet_queue` (line 3051). JOINMATCH records `addr_to_match[addr] = match_id` (line 19387); thereafter gameplay packets from that addr are queued to that match's thread, which is **event-driven** (blocks on `queue.get`, drains up to 120 packets/cycle, line 3068) so gameplay never blocks the lobby. All paths ultimately call `handle_packet`.
- **Capacity**: `MAX_PLAYERS_PER_ROOM` gates `is_full`/`find_available_match`; `is_empty`/`player_count` for teardown checks.
- **Cleanup**: background `session_cleaner` / `offline_player_checker` / `tcp_session_checker` threads; `full_cleanup_player_session` (line 4027), `Match.remove_player` (line 3497), and `cleanup_all_match_sessions` on match end; the match is removed once empty/finished. A Redis-backed reconnect manager mirrors match/player state so a dropped player can rejoin the same match via TCP.

**Net takeaway for a reimplementation**: state is a single `Match` holding a `user_id → dict` map; clients are pure *reporters* (movement, damage requests) while the server owns HP/death/scoring; relay is done by two per-match background threads (fast 30 Hz movement as one combined packet to all; slower ~6.6 Hz full HP/state to all) rather than echoing inside receive handlers; join does an explicit bidirectional PlayerJoin exchange plus a BindPRI rep-id remap; and there is no respawn — only knockdown/revive in team mode.


## Appendix B — Client remote-player requirements (IDA)

I have traced the complete remote-player pipeline. Here is the structured report.

---

# What our FF 1.70.1 client requires from the server to render/sync REMOTE players

All addresses are il2cpp imagebase-0. Receive dispatch hub = `KPDMJKOEHEE::DPLMGOJKKCM` @0x1926ea0. Two independent identity spaces drive everything (this is the key architectural fact):

- **RepID** = the pawn's `Entity.m_UniqueID` → dictionary `MatchGame.m_ReplicationEntitis` (`Dictionary<uint32,ReplicationEntity>`). Used by the **PRI stream (cmd 900)**.
- **PlayerID** = the `IHAAMHPPLMG` value (a uint32; **hibyte = faction/team, low 24 bits = player index**) → dictionary `NFJPHMKKEBF.HOOCHDLKOOG` (`Dictionary<IHAAMHPPLMG,Player>`). Used by **join** and by **combat/state broadcasts** (knockdown/death/etc., resolved via `NFJPHMKKEBF::KAGPBMINBIJ` @0x1a1fad4).

Both IDs originate from the same cmd-101 join and must stay consistent per remote player.

---

## 1. JOIN — cmd 101 (`GKBDLJFGGMI`), handler `OFEBIEPAIKH` @0x1933de8

**Yes, the client fully accepts and spawns REMOTE pawns from cmd 101.** The handler is symmetric: it runs the same spawn path for local and remote, and only *adds* extra local-only setup when `IsLocalPlayer` is true.

Message layout (`GKBDLJFGGMI::UnSerialize` @0x3689708) — the load-bearing fields inside the nested player-info sub-message `DCAFPIJDJEL` (type `OGJKHJAFNHB`):
- `MIJOCMKONAD` — **uint64 account/user id** (must be unique per remote player)
- `IHAAMHPPLMG` — **uint32 PlayerID** (hibyte=team/faction, low24=index). This is the entity identity. `IHAAMHPPLMG::CFFPIACECIG` @0x26a5ea8 splits it: `IOICFFEKAIL = HIBYTE` (team), `JEDDPHIHGKL = value & 0xFFFFFF` (index), `BNFAIDHEHOM = 1<<(value&0x3F)` (team bitmask).
- `DBBDCBDBDIG` — uint64 service/group id, `CBAAEJPGJHB`/`JHKDNBCFKMN` — bools, plus name (`GCJBNAHBGMD`), social sub-msg `IFHIJHODIKE`, platform byte `FBCCMPIJBNC`.

Flow: handler builds the `IHAAMHPPLMG` struct, calls `Player::IsLocalPlayer(userid, PlayerID)` @0x189d980 (branch is local-only: `KEPDHPAAHGP::KPDKKHAINBH`), then for **everyone** calls the spawner `NFJPHMKKEBF::LONDNBHBPDO(userid, groupid, PlayerID, …, msg)` @0x1a39ae4.

Spawner behavior that constrains the server:
- **Dedup key = `IHAAMHPPLMG` (PlayerID).** `HOOCHDLKOOG.ContainsKey(PlayerID)` → if already present it logs a warning and aborts. So **every remote player needs a distinct PlayerID**; the team hibyte must be set correctly (it also keys the team dict `NPLDHOBNMJF` by team byte).
- Creates the pawn (a `PlayerNetwork` for online), stores `Player.KMIBPHEHDNG=userid`, `Player.KFMGKCJMCAM=PlayerID` (`get_PlayerID` @0x187181c returns this), registers into `HOOCHDLKOOG[PlayerID]` and `NIEBEGJADLC[teamByte]`.

**Server must send, per remote player:** one cmd 101 with a unique `MIJOCMKONAD` (userid) and a unique `IHAAMHPPLMG` (PlayerID with correct team hibyte) that differ from the local player's.

---

## 2. PRI — cmd 900 (`DNCBMEDLPGP` @0x194e080) → `GetRepEntity` @0x1c9fe48

**Yes — the client applies replicated HP/state to REMOTE entities, and one cmd-900 packet carries MANY entities.** The route is a loop:
```
while (reader.Position != reader.Length):
    RepID = ReadUInt32()
    ent = MatchGame.GetRepEntity(RepID)          // m_ReplicationEntitis dict lookup
    if ent != null:  ReplicationEntity.OnSyncReplicationData(ent, reader)   // @0x33f9078
    else:            len = ReadFixUInt16(); Seek(len)   // unknown RepID → skip block
```
So the multi-entity block format is `[u32 RepID][FixUInt16 blockLen][payload…]` repeated to EOF. `OnSyncReplicationData` dispatches to the entity's `IRepDataPool.UnSerialize` (vtable slot 30), applies the fields, and fires `OnPRIInitialized` on the first PRI.

**How a remote RepID gets registered — SELF-BIND, not cmd 118.** When the remote pawn starts, `ReplicationEntity::OnStart` @0x33f8e68 calls `OnReplicationBind(get_UniqueID())`, and `COWReplicationEntity::RegisterEntity` @0x268b6d8 calls `MatchGame::RegisterRepEntity` @0x1c9fc40, which does `m_ReplicationEntitis[GetReplicationID()] = entity`. `GetReplicationID` @0x33f915c returns the pool's id, which was set to the pawn's `UniqueID`. **No cmd-118 BindPRI is needed for player pawns** — the spawn (cmd 101) self-registers the RepID. The RepID equals the pawn's `UniqueID` (assigned from the PlayerID at spawn), so the server must stream PRI keyed by that same per-player id it handed out in the join.

Replicated fields (from `Player::OnUserDefineReplicationInfo` @0x190676c and `PlayerNetwork` override @0x1fa09e8): **current HP is a replicated `UInt16`** (with `DataChangedHanlder<UInt16>`), plus max-HP, state flags, and run-speed scales (field ids 50–53). So remote HP/state reach the client purely through cmd 900.

**Server must send, per remote player:** cmd-900 blocks keyed by that player's RepID (its assigned UniqueID), carrying HP/state; may batch all players in one packet.

---

## 3. MOVEMENT — apply `LBCGDBDLEKI` @0x1fa7f54 (interpolated); local upstream = cmd 1001

Remote position/rotation is applied by `PlayerNetwork::LBCGDBDLEKI` @0x1fa7f54, which **buffers into an interpolation target `PLGAAJABBHA` (`HHCBNAPCKHF`), it does NOT snap the transform** — `UpdateKinematics` @0x1fad980 / `UpdateBehavior` smooth toward it (interpolation). Two guards matter:
- **Sequence gate:** `if (KINJCKMOGIM < incomingSeq)` — a per-player monotonic move sequence; older/out-of-order moves are dropped.
- **`if (!IsLocalPlayer)`** — network position is applied to REMOTE pawns only; the local pawn is client-predicted and never overwritten.

It is fed by the replicated synced-state handlers:
- `PushPlayerSyncedStateData(CIBBLFMOMLK, seq)` @0x1fa8990 — full state.
- `PushPlayerSyncedOptimizedStateData(BMMNIPHPNKI, seq)` @0x1fa7938 — bandwidth-optimized form: 3 quantized angle bytes decoded via `Quaternion.AngleAxis` into body + aim rotation.
- `PushPlayerSyncedPosition` @0x1fa872c — position-only.

These three are registered as the pawn's replicated-property change handlers (method-pointer table at 0x606ccc0–0x606cce8) — i.e. remote movement/state rides the **replication/state-sync channel** (the same PRI path, cmd 900) rather than a separate per-frame move opcode. The `CIBBLFMOMLK`/`BMMNIPHPNKI` payload carries: compressed position (`CCIKDFGDBAM`), body-move dir, aim dir, move-platform id (`IABJNDBNDBK`), movement state (`GHGCGGOLKIP`), speed (`LMNBBBCKMGB`), flags, and the sequence.

Contrast with the local player: the client **sends** its own movement upstream as cmd 1001 (client→server input). The server **does not echo the local player's own movement back** (the `if(!IsLocalPlayer)` guard would ignore it anyway); it only relays *other* players' state.

**Server must send, per remote player:** a synced-state update (position + body rot + aim rot + movement state + speed + a monotonic per-player sequence), delivered on the replication channel; the client interpolates.

---

## 4. DAMAGE / DEATH

Client→server hit reporting is cmd 106; observers are updated two ways:

**Damage (HP):** For an observer watching one remote player hit another, damage manifests as the victim's **HP dropping via the PRI (cmd 900)** — HP is the replicated `UInt16` field (§2). The heavy `PlayerNetwork::TakeDamage` @0x1fb049c (damage numbers, hit reaction) is a virtual run locally by the attacking client; other clients just see the replicated HP change and update the health bar/hit FX. So **the server broadcasts damage-to-others as an HP value in cmd 900**, not a per-observer damage packet.

**Knockdown (downed):** dedicated broadcast — message `NKDBFGLPCCF`, handler `JFCAKCFEAEN` @0x193ed20. It resolves the victim pawn via `NFJPHMKKEBF::KAGPBMINBIJ(PlayerID)` (the *player dict*, not the RepID dict), casts to `PlayerNetwork`, calls `SyncKnockDown` @0x1fb3464, and dispatches `PLAYER_KNOCKDOWN`. Payload carries victim PlayerID (`IHAAMHPPLMG`), attacker PlayerID (`MINLJOJIILD`), weapon id (`PIAMIOFEBKF`).

**Death:** `PlayerNetwork::Dead(int, IHAAMHPPLMG killer, bool, bool)` @0x1fb3358 (over `Player::Dead` @0x189fd8c). It is driven by the same victim-targeted broadcast pattern (resolve by PlayerID via `KAGPBMINBIJ`, then call `Dead` on the pawn) — carrying the victim PlayerID and the killer PlayerID. (This matches the cmd-107 death opcode in our notes; the broadcast is one of the ~50 `KAGPBMINBIJ`-resolving handlers in `KPDMJKOEHEE`.)

**Server must send, per remote player event:** HP via cmd 900 for ordinary damage; a knockdown broadcast (`NKDBFGLPCCF`: victim PlayerID + attacker PlayerID + weapon) to down a player; and a death broadcast (victim PlayerID + killer PlayerID) to kill one. All combat broadcasts key on **PlayerID (`IHAAMHPPLMG`)**, resolved through the player dict — not the RepID.

---

## 5. Local-vs-remote gating throughout

`Player::IsLocalPlayer(userid, IHAAMHPPLMG)` @0x189d980 is the single arbiter: returns true iff the PlayerID's index matches the static local sentinel `IHAAMHPPLMG::NCKFFKCHCBN`, **or** `GameFacade.GetLocalPlayerUserID() == userid`. For a remote player, **both the userid and the PlayerID must differ from the local player's** — otherwise the client treats the remote as itself and mis-routes it.

- **Join** (@0x1933de8): gates only the local-only extra init; spawn runs for all. The spawner dedups by PlayerID, so distinct PlayerIDs are mandatory.
- **PRI** (@0x194e080): identity is the RepID (UniqueID) in `m_ReplicationEntitis`; each remote pawn self-binds a distinct RepID at spawn. Unknown RepIDs are skipped, so the server must use exactly the ids the client registered.
- **Movement** (@0x1fa7f54): `if(!IsLocalPlayer)` prevents network state from clobbering the predicted local pawn; remote pawns interpolate to the buffered target under a monotonic sequence.
- **Damage/death**: resolved by PlayerID through the player dict; the handlers also compare against `CurrentLocalPlayerID` to decide first-person vs observer UI, but apply to whichever pawn the PlayerID resolves to.

**Bottom line for the reimplementation:** assign each remote player two consistent ids at join — a unique `MIJOCMKONAD` (userid) and a unique `IHAAMHPPLMG` (PlayerID, correct team hibyte) — then (a) send cmd 101 to spawn, (b) stream cmd 900 keyed by that player's RepID for HP/state (and the synced movement/state property, interpolated), and (c) emit PlayerID-keyed combat broadcasts for knockdown/death. Never reflect the local player's own userid/PlayerID onto a remote, and never echo the local player's cmd-1001 movement back.


## Appendix C — Our current single-player code map

I now have a complete picture of the architecture. Here is the file-by-file map and the single-player assumption inventory.

---

# match-server architecture map (current state)

## 1. Connection → session → match; server loop; shared state

**There is NO shared match object. ALL state is per-session (per UDP connection).** A "match" is entirely emergent from one `session` streaming to one client.

- `main.go` — `serve()` is a **single-threaded receive loop** over one UDP socket (`conn.ReadFromUDP`). No per-connection goroutine for reads; every datagram is decoded on the one loop. Sessions are looked up in a package-global `sessions map[string]*session` keyed by `remote.String()`. `sessionsMu` guards it. That map is used for **nothing except `kickAllAndExit`** — sessions never see each other. `s.dispatch(p)` runs the handler inline (with panic recovery) on the receive goroutine.
- The only per-session goroutines are spawned from the CS loop: `csSyncLoop`, `serverTimeLoop`, `runSafeZone`, `healMedkit`, `dropOverriddenAfterEquip`.
- `session.go` — the `session` struct **IS the match**: it holds the local `player joinPlayer`, the single `bot joinPlayer`, `botEntity`, `round`, `teamScore [2]uint8`, `arena`, the economy (`coins`, `equipment`, `weapons`, `clientUIDs`, `containers`), the `walls`, and the HP map `hp map[uint32]uint16`. Writes go only to `s.remote` (`s.write` → `conn.WriteToUDP(wire, s.remote)`). There is no fan-out primitive — every send targets exactly one client.

**What breaks for N players:** there is no object that represents "the match" independent of a connection, so two clients each run their own private match with their own arena, round counter, score, and HP map, streamed only to themselves. Nothing is shared or broadcast.

## 2. The CS sync loop (`cssync.go`)

- `startCSSync` → `go csSyncLoop()` — one loop **per session**, guarded by `s.syncStarted`.
- `csSyncLoop` (lines 35–120): seeds `s.coins`, sets `matchStart`, starts `serverTimeLoop`, seeds `round=1`/`botEntity=botEntityID`, `initHP`, `bindPRIs`, `shopWarmup`, then the round loop `for s.round <= maxRound && s.teamScore[0] < roundsToWin`. Round decision (82–96): `localWon := s.entityHP(playerEntityID) > 0`; scores `teamScore[0]` (local) vs `teamScore[1]` (bot); coin award from `s.roundKills`.
- `streamPhase` (127–160): the streamer. Every ~300ms it `sendVar`s to **this one client**: `s.priPayload()` (cmd 900), `CSGRIInit`, `CSGRIPhase`, `CSGRIMatchPoint` (cmd 901). Fight-phase exit is `untilBotDead && (entityHP(s.botEntity)==0 || entityHP(playerEntityID)==0)`.
- `priPayload` (201–223): builds the PRI stream containing **exactly two entities** — `playerRepID` (local, with live coins/award/faction) and, if alive, `botRepID` (the bot). Scores are packed from `teamScore[0]/[1]`.
- `bindPRIs` (385–392): sends cmd 118 binding **exactly two RepIDs** — `{playerRepID → playerEntityID}` then `{botRepID → s.botEntity}`. Comment notes the client "adopts the FIRST EntityType=1 binding as its own."

**What must change:** `priPayload` must iterate ALL players+bots in a shared match and emit a PRIEntity per one, using per-player RepIDs/entity IDs/factions/scores. `bindPRIs` must bind every participant. `streamPhase`/`csSyncLoop` must run **once per match** and fan the same GRI/PRI out to every member's `session.write`, not per-session with hardcoded two entities. GRI/round/phase/arena/score must move to a shared match object so all clients see the same round and timers.

## 3. The bot (`player.go`, `round.go`, `cssync.go`, `combat.go`)

The bot is a single passive dummy that stands in for "the opponent" and is the win/lose condition:
- **Identity/spawn** (`player.go` `botPlayer`, consts `botAccountID/botName/botEntityID/botRepID/botFaction`): fixed entity `0x02000002`, RepID `1001`, faction `1`, spawned `botSpawnOffset` (2m) in front of the local player.
- **Spawned**: `handleJoinMatchPost` (handlers.go 100–109) sends the bot's cmd 101; `respawnBot` (round.go 143–149) re-joins + teleports the same entity each round.
- **Streamed**: `priPayload` (cssync.go 219–220) and `bindPRIs` (388).
- **Damaged / win condition**: `initHP` seeds `s.botEntity: maxHP`; `streamPhase` ends the round on bot death; `csSyncLoop` scores off `localWon`; `killEntity` (combat.go 99) credits `roundKills` when `killer==playerEntityID && victim==s.botEntity`; `deathPos`/`spectateTarget` special-case `s.botEntity`.

**Must be replaced** by real opponents: every `s.botEntity`/`s.bot`/`botRepID`/`botFaction`/`respawnBot` reference, the two-entity PRI/Bind, and the round-win test (`bot dead`) must become "enemy team eliminated / real opponents' HP."

## 4. Player identity — what is single-player-baked (`player.go`)

- `playerEntityID = 0x01000001`, `playerRepID = 1000`, `localFaction = 0`, `maxHP` — **compile-time consts**, used everywhere as *the* player.
- **Critical bake:** `resolvePlayer` (player.go 73–101) hardcodes `EntityID: playerEntityID` in the struct literal and **never overrides it from the JWT**. So **every connecting client is told it is entity `0x01000001`, RepID `1000`, faction `0`, team hibyte `1`.** Two real players would be assigned identical entity/RepID/team and collide completely.
- `botEntityID/botRepID/botFaction` — the single fixed opponent.
- `localTeamID = 1 / enemyTeamID = 2` (round.go 17–20) — hardcoded two-team hibytes.
- No uid/entity/RepID **generators** for players exist. Only `nextUIDLocked` (item instance ids, purchase.go 242) and `nextWallLocked` (gloo). There is no allocator that hands distinct entity IDs / RepIDs / team hibytes / faction sides to N joining players — the reference `PlayerIDGenerator` scheme (hibyte=team, low24=slot) is described in comments but **not implemented**.

## 5. Damage / HP / round (`combat.go`, `round.go`)

- `combat.go` — `s.hp map[uint32]uint16` is per-session; `initHP` seeds **only** `{playerEntityID, s.botEntity}`. `entityHP` returns `maxHP` for anything untracked. `applyDamage` mutates this session's map; `killEntity` only knows two identities (`playerEntityID`, `s.botEntity`, killer `0`=zone); `heldWeaponData`/`SkinForWeapon` read only `s.player`. `handleTakeDamage` applies damage on the **shooter's own session** — a hit on a real remote player would land in the wrong session's HP map (the victim's session is a different object).
- `round.go` — round decided by `localWon = entityHP(playerEntityID) > 0` (bot dead ⇒ win). `roundTransition` reseeds `s.hp = {playerEntityID, s.botEntity}`, repositions only the local player + the one bot, `respawnBot`, `respawnLocalPlayer`. Scores are the 2-slot `teamScore`. `roundResult`/`matchEnd` compute VICTORY/DEFEAT purely from the one local player vs the one bot.

**Assumes exactly one player + one bot**: HP map has two keys, damage is authored on the attacker's session, and win/lose is "my bot died / I survived."

## 6. Join flow (`handlers.go`)

- `handleJoinMatchPost` (cmd 440, lines 90–114): reassembles the prepare_token → `resolvePlayer` (→ always entity `0x01000001`) → `choosePlayerSpawn` picks a **random arena per join** (not per match) → sends cmd 100/101/130 for the local player → immediately **spawns the bot** (cmd 101) → `startCSSync`. There is **no matchmaking/lobby/roster step**: a join instantly creates a private 1v1-vs-bot match. No notion of "wait for other players," no assignment of a shared arena, no broadcasting this player's cmd 101 to other clients (or vice-versa).
- `handleHello`/cmd 5 reconnect (63–76): if `!syncStarted`, falls back to `resolvePlayer("")` (entity `0x01000001` again) and resumes the CS loop. Reconnect identity is not tied to any account/roster — it just re-adopts the single baked identity.

## Appendix D — Proposed optimized tick-based architecture

I have enough context now. I read the current threading model in full: a single shared UDP socket with one `serve()` recv goroutine, `sessions map[string]*session` guarded by `sessionsMu`, and per-session `csSyncLoop` + `serverTimeLoop` + per-Fight `runSafeZone` goroutines all sleeping and all writing directly to the shared conn, with three per-session mutexes (`mu`, `invMu`, `hpMu`) carefully ordered. Here is the design.

---

# Optimized multiplayer architecture — Go CS match server

## Verdict up front

Move to an **actor-per-match** model: **one goroutine owns all of a match's mutable state** (registry + round/phase/zone/clock/scores + every player's HP/coins/inventory), driven by **one `select` loop with three tickers**. Net-recv stays a single shared-socket goroutine that only parses and posts events. Each connection gets **one writer goroutine** that owns its seq/order. This deletes the 3 sleeping goroutines-per-player and all three mutexes.

**Key enabling fact I verified in `packet.go`:** `Packet.Encode` computes CRC7 over the body only, and VAR packets (cmd 900/901/1000) are `SendOption=4`, `Flags=0` — plaintext, unreliable, no per-connection seq/order and no address in the bytes. So a broadcast PRI/GRI/clock packet produces **identical wire bytes for every player** → encode **once per tick**, fan the same `[]byte` out to N players. That is the whole optimization, and the current serializer `message.SyncPRI([]PRIEntity)` already packs many entities into one cmd 900.

    mailbox chan event      // single-owner command queue (buffered ~256)
    quit    chan struct{}
    done    chan struct{}   // closed when run() exits (reap signal)

// join (no locks). The Writer separately owns the transport/send path.

}

// so session.mu disappears entirely.

    addr       *net.UDPAddr
    key        []byte
    ch         chan outItem // buffered ~128
    seq, order uint16       // owned by the writer goroutine only

## 3. Tick model

Replace **N × (csSyncLoop + serverTimeLoop + runSafeZone)** with **one** ticker set per match. Three cadences, chosen by how fast the data actually changes:

| Stream | Cmd | Rate | Why |
|---|---|---|---|
| **Movement relay** (remote player positions) | pos replication (145/144-class) | **~16 Hz (60 ms)** | Only thing that must look smooth; batched into one packet/tick |
| **State sync** PRI + GRI | 900 + 901 | **~5 Hz (200 ms)** | HP/coins/score/phase change rarely; unreliable, resent for drop-tolerance (was 300 ms) |
| **Server clock** | 1000 | **~4 Hz (250 ms)** | Re-anchors the client's zone-lerp clock; keep the tuned 250 ms |

Discrete, **reliable** events (death 107, zone-change 117, round-result 409, join 101, bindPRI 118, inventory 174, teleport 145) are **not** on a ticker — they fire from the state machine / handlers and go per-player through `p.out.SendReliable`.

**Two structural conversions do the heavy lifting:**
1. **`runSafeZone` goroutine → a `stepZone()` call inside the state tick.** Each state tick recomputes the shrink radius (`lerpRadius`) and, on the 2 s damage cadence, walks the player list applying out-of-zone damage. No per-Fight goroutine, no `time.Sleep`.
2. **The blocking round loop (`csSyncLoop`/`streamPhase`/`roundTransition` with `time.Sleep`) → a deadline-driven state machine.** State + `phaseDeadline` live in `Match`; `advancePhase(now)` (called each state tick) checks `now >= phaseDeadline` (or "bot dead / player dead") and transitions, doing the discrete reliable sends on the edge. Warmup → Prepare → Fight → Post → Introduction → next round → Ended, exactly the current sequence, just event-driven instead of sleep-driven.

### Tick-loop pseudocode

```go
func (m *Match) run() {
    defer close(m.done)
    tickMove  := time.NewTicker(60 * time.Millisecond)   // ~16 Hz  position relay
    tickState := time.NewTicker(200 * time.Millisecond)  // ~5  Hz  PRI(900)+GRI(901)+zone step
    tickClock := time.NewTicker(250 * time.Millisecond)  // ~4  Hz  SyncServerTime(1000)
    defer tickMove.Stop(); defer tickState.Stop(); defer tickClock.Stop()

    for {
        select {
        case ev := <-m.mailbox:            // join/leave/damage/pos/purchase/place/pickup/...
            m.handle(ev)                   // single-owner mutation — no locks
            if m.state == Ended && m.empty() { m.mgr.retire(m.id); return }

        case now := <-tickClock.C:
            m.broadcast(frameVar(packet.CmdSyncServerTime,
                message.SyncServerTime(m.clockTick(now))))   // encode ONCE, fan out

        case now := <-tickState.C:
            m.advancePhase(now)            // state machine: buy->fight->post->intro->next; reliable edges
            m.stepZone(now)                // shrink + out-of-zone damage over the player list
            m.broadcast(m.encPRI())        // ONE cmd 900 for the WHOLE match
            m.broadcast(m.encGRI())        // ONE cmd 901 (round/phase/scores/matchpoint)

        case <-tickMove.C:
            if wire := m.encMoves(); wire != nil { m.broadcast(wire) }  // batched positions

        case <-m.quit:
            return
        }
    }
}

// broadcast: VAR bytes are identical for all players (verified: CRC over body, no addr,
// no per-conn seq) -> enqueue the SAME slice to each connected player, non-blocking.
func (m *Match) broadcast(wire []byte) {
    for _, p := range m.players {
        if p.out == nil { continue }       // bot / disconnected
        p.out.SendRaw(wire)                // drop-on-full (unreliable, superseded next tick)
    }
}

// encPRI builds the shared cmd 900 ONCE: every live player's + bot's HP/coins/score block.
func (m *Match) encPRI() []byte {
    ents := make([]message.PRIEntity, 0, len(m.players))
    for _, p := range m.players {
        if p.isBot && !p.alive { continue }                 // drop dead bot (as today)
        score := message.PackScore(m.teamScore[p.team], m.teamScore[p.team^1])
        ents = append(ents, message.PRIEntity{
            RepID: p.repID,
            Block: message.PRIHPBlock(p.hp, p.maxHP, uint16(p.coins), uint16(p.award), score, p.faction),
        })
    }
    return frameVar(packet.CmdPRISync, message.SyncPRI(ents))
}
```

```go
func (w *Writer) loop() {
    for it := range w.ch {
        var wire []byte
        if it.raw != nil {
            wire = it.raw                          // pre-framed VAR broadcast
        } else {                                   // reliable: writer owns seq/order -> no mutex
            wire, _ = (&packet.Packet{SendOption: packet.SendReliable, Cmd: it.cmd,
                SeqID: w.seq, OrderID: w.order, Flags: packet.FlagEncrypted, Payload: it.body}).Encode(w.key)
            w.seq++; w.order++
        }
        w.conn.WriteToUDP(wire, w.addr)
    }
}
func (w *Writer) SendRaw(b []byte)                { select { case w.ch <- outItem{raw: b}: default: } } // drop unreliable
func (w *Writer) SendReliable(cmd uint16, b []byte) { w.ch <- outItem{cmd: cmd, body: b} }              // block ok (rare)
```

### Goroutine census (the health win)

- **Before:** `1 recv + ~3 × P` (csSyncLoop + serverTimeLoop + runSafeZone per player), all on `time.Sleep`, all writing the shared conn.
- **After:** `1 recv + M match + P writers`. For 8 matches × 8 players (P=64): **~192 sleeping goroutines → 73**, and none spin on `time.Sleep` — they park on `select`. Parallelism is across matches (each match goroutine is independent, scheduler spreads them over cores); serial within a match, which a single CS match's few-hundred-events/sec load never strains.

## 4. Concurrency choice: **single-owner mailbox** (not RWMutex)

**Choice: mailbox/actor per match.** Every state change — join, leave, damage, position, purchase, wall-place, pickup, phase edge, tick — serializes through one goroutine's `select`. Producers post typed events; droppable ones (position) use non-blocking send, must-not-drop ones (join/leave/damage/purchase) block.

**Why, specifically for 8p × many matches:**

- **It deletes the locks by construction.** The current code already carries three mutexes with a documented ordering (`invMu` before `hpMu`, the `mu` seq lock). Every new feature multiplies lock-ordering hazards. Single-owner state needs **zero** game mutexes — no deadlocks, no races, by design.
- **The tick is a hot iterating reader.** Building the broadcast walks the whole player map every 200 ms (and moves every 60 ms). Under an RWMutex you'd hold the read lock across serialization while damage/join/leave writers wait; match state is **write-heavy** (every hit, every position, every buy), so the RWMutex degenerates toward a plain mutex that serializes everything anyway — the actor gets that same serialization *without* the lock machinery or the risk of a slow handler stalling the tick behind a held lock.
- **Parallelism lives at the right granularity.** You don't want 8 players in one match truly parallel (they mutate shared round/zone/score); you want *many matches* parallel. One goroutine per match delivers exactly that: independent matches scale across cores; within a match, determinism and trivial correctness.
- **Back-pressure is explicit.** Buffered mailbox (~256); a flooded position stream drops instead of blocking recv, and it's superseded next tick anyway.

The one rule: **handlers must not block inside `run()`.** They never do — all network output is a non-blocking enqueue to a `Writer` (§3), and all logic is arithmetic over in-memory state.

> Scope note: the **Manager** registry (§6) uses a plain `sync.Mutex`, not an actor — that's correct. Its critical sections are tiny and low-frequency (create/route/reap), never on the tick hot path. "Mailbox vs RWMutex" is a question about *match* state; the manager's little maps are fine under a short Mutex.

## 5. ID / team allocator

Preserve the reference `PlayerIDGenerator` semantics I confirmed in `player.go`: **entity id hibyte = team**, two entities are teammates iff same hibyte (local `0x01000001` = team-hibyte 1; bot `0x02000002` = team-hibyte 2). Bands: team A → hibyte 1, team B → hibyte 2; low-24 = per-team slot (1..4). RepIDs in a disjoint band `1000 + globalSlot`; gloo/prop RepIDs stay high (`wallSeq`-based, e.g. 5000+) so they never collide with players.

```go
const (
    maxPerTeam    = 4
    maxPlayers    = 8
    minToStart    = 2
    playerRepBase = 1000
    teamShift     = 24
)

type idAllocator struct {
    usedSlots [2]uint8 // bit i set = team t slot i (0..3) in use
    repUsed   uint8    // bit j set = RepID offset j (0..7) in use
}

// allocate: balanced team (fill the smaller; tie -> team 0), lowest free slot, banded
// entity id, disjoint RepID. ok=false when the match is full (8).
func (a *idAllocator) allocate() (entityID, repID uint32, team, faction byte, ok bool) {
    ca, cb := bits.OnesCount8(a.usedSlots[0]), bits.OnesCount8(a.usedSlots[1])
    if ca+cb >= maxPlayers { return }
    team = 0
    if cb < ca { team = 1 }                              // smaller team; tie -> A
    slot := lowestClear(a.usedSlots[team], maxPerTeam)   // 0..3
    if slot < 0 { team ^= 1; slot = lowestClear(a.usedSlots[team], maxPerTeam) }
    if slot < 0 { return }
    a.usedSlots[team] |= 1 << slot
    entityID = (uint32(team+1) << teamShift) | uint32(slot+1) // hibyte=team+1, low24=slot+1
    faction  = team                                          // team 0 -> faction 0 (left gate)
    r := lowestClear(a.repUsed, maxPlayers)
    a.repUsed |= 1 << r
    repID = playerRepBase + uint32(r)
    ok = true
    return
}

// free: retire a leaver's slot + RepID back to the pools (rejoin reuses the lowest free).
func (a *idAllocator) free(entityID, repID uint32) {
    team := byte(entityID>>teamShift) - 1
    slot := byte(entityID&0xFFFFFF) - 1
    a.usedSlots[team] &^= 1 << slot
    a.repUsed &^= 1 << byte(repID-playerRepBase)
}
```

- **Cap 8 / min 2:** `allocate` refuses the 9th; match won't leave `Lobby` until `≥ minToStart` present (seed a bot-`Player` on team B to reach 2 during single-player bring-up, exactly reproducing today's static-bot fight).
- **Balanced:** each joiner fills the smaller team → 4v4 max, self-heals on leave.
- **Reuse/retire safety:** free the slot only *after* the player is removed from `players` and a leave/despawn is sent, so no in-flight PRI still references the freed RepID (the next tick's `encPRI` simply omits it). Bitsets make alloc/free O(1) and deterministic.
- **"Self is first" is a per-connection send concern, not an id concern:** each client's own `BindPRI` (cmd 118) lists *its* entity first (the client adopts the first `EntityType=1` binding as self), then the rest of the roster. The allocator only guarantees correct team hibytes + unique RepIDs.

## 6. Match manager

```go
type Manager struct {
    mu       sync.Mutex          // guards matches + joinable ONLY (tiny critical sections)
    matches  map[uint64]*Match
    joinable []*Match            // Lobby/Warmup matches with < 8 players
    byAddr   map[string]*Player  // recv demux: remote addr -> Player -> Player.match
    nextID   uint64
    conn     *net.UDPConn
    factory  MatchFactory        // SEAM: in-proc goroutine now, process-spawn later
}
```

- **Route a connection:** the recv goroutine parses the join (cmd 439/440), verifies the token (`resolvePlayer`), then `mgr.Assign(player)`: under `mu`, pick a `joinable` match (or `factory.New()` a fresh one), post `evJoin{player, replyCh}` to its mailbox, release `mu`. The **match goroutine is authoritative on admission** — its `evJoin` handler re-checks `len(players) < 8 && state <= Warmup`, allocates ids, spawns the newcomer for existing players (broadcast cmd 101) and all existing players for the newcomer (cmd 101 ×N + bindPRI self-first), and replies ok/bounce. On bounce (filled between pick and admit) the manager retries / creates a new match. This keeps capacity race-free without the manager tracking exact live counts.
- **Enforce 2–8:** admission caps at 8; `Running` requires `≥ 2`. Once started, the match runs to completion even if it dips below 2 (remaining players / bot fill), matching CS.
- **Reap:** when the last player leaves or the match ends, the match goroutine calls `mgr.retire(id)` (short `mu` section: delete from `matches`/`joinable`) and returns from `run()` (closing `done`). Add a **grace window** before reaping an emptied-but-not-ended match so the **reconnect path** (cmd 5, which today resumes by addr) can re-attach to the *same* match rather than spawning a stale one.
- **Process-per-match seam (leave clean, don't build):** the manager only ever talks to a `MatchHandle` interface — `Post(event)`, `Capacity()`, `Done()`. Today `factory.New()` returns a `*localMatch` wrapping an in-proc `*Match` + its mailbox. Later, a `procMatch` implementation spawns an OS process on its own UDP port and returns a handle backed by an IPC/redirect; routing code is untouched because it never reaches past the interface. Define the interface now, ship only the local impl.

## 8. Gotchas to verify during bring-up

- **Encode-once is provably safe** for VAR (CRC7 over body, no addr, no seq, `Flags=0`) — confirmed in `packet.go:Encode`. Reliable packets (101/107/117/174…) carry per-conn seq/order and encryption, so they **cannot** share bytes — send them per-player via `SendReliable` (fine; they're infrequent).
- **Coins in the shared PRI:** each player's own coins ride in *their* RepID block; every client receives all blocks but the shop UI reads only its own pawn's PRI. Put each player's real coins in their block (don't put the local player's coins everywhere as `priPayload` does today). Confirm on the client that a teammate's coin field never bleeds into your shop.
- **BindPRI ordering is per-connection:** each client's cmd 118 must list its own entity first, then the roster — the "first EntityType=1 = self" rule is per-recipient, not global.
- **Zone step vs the old ticker:** `stepZone` must keep the `zoneClientLag` compensation and the 2 s damage cadence when it moves off its own goroutine, or out-of-zone damage will land while players are visibly inside the circle.
- **`walls`/`containers` are match-world:** once a 2nd player joins, a wall placed by A must be visible/shootable by B — promote them from per-player to match-shared, keyed by owner RepID, when you do step 5.
